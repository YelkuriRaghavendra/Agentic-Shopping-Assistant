# Vikrai — Presentation Guide

## For Panel Presentation (10 min talk + 5 min Q&A)

## ELEVATOR PITCH (30 seconds)

> "Vikrai is an agentic shopping assistant that turns a conversation into a purchase. Unlike static search bars, Vikrai understands what you want through dialogue — ask for running shoes, upload a photo of your outfit, compare products side-by-side — and complete the purchase in the same conversation. It's built on a 4-service architecture with 3-way hybrid RAG retrieval, GPT-4o vision, and Stripe-powered checkout."

---

## PROBLEM STATEMENT (1 minute)

**The problem:** Online shoe shopping is broken.

- You search "casual shoes" on Amazon → 50,000 results. No guidance. No conversation. You're on your own.
- You don't know your size in that brand. You don't know what color matches your outfit. You don't know which is better value.
- 70% of shoppers abandon their cart because the experience is overwhelming.

**Our insight:** In a physical shoe store, a good salesperson asks you 2 questions and pulls out 3 perfect options. We built that salesperson as an AI agent.

**What Vikrai does differently:**
- Asks 2 smart questions, not 20 filters
- Understands photos — upload your outfit, get matching shoes
- Remembers you across sessions — your size, your brands, your friend's birthday
- Completes the purchase in the same conversation — no redirect to a separate checkout page

## ARCHITECTURE SLIDE (2 minutes)

Show the Mermaid diagram from `00-FULL-ARCHITECTURE.md`. Talk through it:

**30 seconds — the 4 services:**
> "4 services, each with a different scaling pattern. Chat backend is CPU-bound — LLM calls. RAG service is memory-bound — vector search. Checkout is I/O-bound — Stripe webhooks. They scale independently."

**30 seconds — the agentic pattern:**
> "Every message goes through a 12-step pipeline. The LLM makes TWO calls per message: first it decides which tool to call — search, compare, size advice, checkout. Then it generates a natural response using the tool's results. 14 tools available. The LLM picks. We don't hardcode routing."

**30 seconds — 3-way hybrid RAG:**
> "Dense embeddings for semantic meaning — 'comfortable' finds 'cushioned'. BM25 sparse search for exact keywords — 'Nike Air Max 270' finds that exact product. Reciprocal Rank Fusion merges both lists. Cross-encoder reranks the top candidates. This is the same architecture Google and Bing use internally."

**30 seconds — the commerce layer:**
> "Checkout sessions with Stripe payment links. Orders with append-only audit trail. BullMQ for async processing. UCP protocol for merchant integration with signed requests and circuit breakers. Orders get indexed back into RAG so the bot can answer 'where's my order?'"

## COMPETITIVE POSITIONING

**If asked "Why not just use Shopify Sidekick / Amazon Rufus?":**

> "Three differences:
> 1. **Open platform** — Sidekick is locked to Shopify. Rufus is locked to Amazon. Vikrai works with any merchant via UCP protocol.
> 2. **Full funnel** — Most AI assistants stop at product discovery. We go from conversation to comparison to payment to order tracking in one interface.
> 3. **Multi-modal** — Upload a photo of your outfit, get matching shoes. Rufus can't do that. Sidekick can't do that."

**If asked "What about Perplexity Shopping?":**

> "Perplexity aggregates across stores but can't complete a purchase. We own the full transaction — checkout, payment, order, returns. That's the monetization path."

## ANTICIPATED PANEL QUESTIONS + ANSWERS

### Architecture Questions

**Q: "Why 4 microservices for a hackathon? Isn't this over-engineering?"**
> "Each service has a fundamentally different scaling pattern and tech stack. Chat backend is Python + FastAPI for LLM integration. Checkout is NestJS + TypeScript for Stripe SDK. RAG is Python + pgvector. A monolith would force us to deploy all three together and scale them as one unit. The separation also lets us swap components — replace pgvector with Pinecone, or replace Stripe with Razorpay — without touching the other services."

**Q: "Why GPT-4o and not Claude or Gemini?"**
> "Azure OpenAI gives us enterprise SLA, GDPR compliance, and the same API for both text and vision. The LLM client is abstracted behind an interface — adding Claude as a fallback provider is a one-day change. We chose GPT-4o because it has the best tool-calling accuracy in our testing."

**Q: "Why not use LangChain or LlamaIndex?"**
> "We built the agentic loop ourselves — 200 lines of code in ChatService. LangChain adds 50+ dependencies, abstractions we don't need, and makes debugging harder. Our pipeline is explicit: 12 steps, each testable independently. We can explain every line."

### RAG Questions

**Q: "Your hybrid search uses ts_rank. That's not real BM25."**
> "Correct. ts_rank with normalization flag 1 approximates BM25's document length normalization but doesn't have the k1 term frequency saturation parameter. For production, we'd use Elasticsearch or a dedicated BM25 implementation. We chose ts_rank because it works with our existing PostgreSQL setup — no additional service to deploy."

**Q: "What's your retrieval precision?"**
> "We don't have automated eval metrics yet. That's the biggest gap. We've tested manually across ~30 queries and the 3-way hybrid consistently outperforms vector-only — especially for brand-specific queries like 'Nike Air Max' where BM25 exact match dominates. The cross-encoder reranker catches cases where the vector search returns semantically similar but wrong products."

### Product Questions

**Q: "Show me the conversion funnel."**
> "We don't have analytics instrumentation yet — that's a post-hackathon priority. What we can show is the full funnel working: conversation → product discovery → comparison → checkout → payment → order confirmation. The path exists end-to-end."

**Q: "What happens when the LLM hallucinates a product?"**
> "Two defenses: First, the output guardrails check that every [P1] citation in the response maps to a real product from RAG. If the LLM invents a product name that wasn't in the retrieved results, the guardrail flags it. Second, we never show product information that didn't come from RAG — prices, ratings, URLs all come from the database, not the LLM."

**Q: "How do you handle returns?"**
> "The order service supports FULFILLED → RETURN_REQUESTED transitions. All mutations are transactional with the append-only audit log — if the audit write fails, the entire operation rolls back. The return request triggers a RAG re-index so the bot can reference the return status in future conversations."

### Business Questions

**Q: "What's the monetization model?"**
> "Platform fee per transaction — similar to Shopify's model. We facilitate the sale, the merchant fulfills. The UCP protocol means any merchant can integrate. Revenue scales with GMV, not with the number of conversations."

**Q: "Who's the customer? The merchant or the shopper?"**
> "The merchant. They embed Vikrai as their shopping assistant. The shopper is the end user. Think of it as Intercom for e-commerce — merchants pay, shoppers benefit."

## THINGS TO AVOID

- Don't demo checkout if Stripe isn't working — show product discovery instead
- Don't say "we didn't have time" — say "we prioritized X over Y because Z"
- Don't read the architecture diagram — tell a story of one message flowing through
- Don't compare yourself to ChatGPT — you're not a general chatbot, you're a commerce agent
- Don't show more than 3 demo flows — depth beats breadth
- Don't apologize for the suggestion chips — they work most of the time now
